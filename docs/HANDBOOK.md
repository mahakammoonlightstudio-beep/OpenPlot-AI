## Getting started

OpenPlot AI is a local-first chat and story studio. Your chats, projects, story bible and settings live in one SQLite file on your machine — only the model request leaves the app.

## 1. Add a provider
Open Settings → AI Providers and either use **Smart setup** (pick a preset → paste a key → test) or add a provider manually.

Every provider row needs:
- **Base URL** — the API root, for example `https://api.openai.com/v1`.
- **API key** — stored encrypted when your OS vault is available.
- **Models** — fetched with *Test & fetch*, or typed by hand.

## 2. Pick a model
Settings → Settings → Models lists every model with its capability chips. Choose one as the default, or leave **Auto (recommended)** and let each chat decide.

## 3. Start a chat
`Ctrl+N` creates a chat. Type, press `Enter` to send, `Shift+Enter` for a new line. `Ctrl+K` opens the command palette from anywhere.

## 4. Give it a project (optional)
A project holds a story bible, chapters and a context block. Attach a project to a chat and the model sees your canon instead of guessing.

> Continue with the chat, files, skills and story bible articles, in that order.

## Chat basics

## Sending
- `Enter` sends; `Shift+Enter` inserts a newline.
- The composer grows to about eight lines, then scrolls.
- `Esc` closes the model or skills popover.

## Stopping and regenerating
While a reply streams the send button becomes **Stop**. Stopping keeps the partial text — it is a real message, not a discard.

**Regenerate** re-runs the last assistant turn. The previous reply stays in the message menu so you can compare.

## Per-chat overrides
The header shows the model, the token meter and the project chip. Each chat keeps its own:
- model and temperature override,
- system prompt (replaces the global one for this chat only),
- thinking setting and budget,
- session goal — a pinned instruction injected into every prompt,
- per-chat skill opt-outs.

## Organising
- **Folders** group chats in the sidebar; move a chat into a folder from its menu.
- **Pin** keeps a chat at the top.
- **Rename** from the chat row or the header.
- Deleting a chat deletes its messages and attached files. There is no undo — export from Settings → Data first if the chat matters.

## What the model actually sees
Open Settings → agent.md and press **Preview prompt** to inspect the exact system prompt for your next message: system, agent.md, project, memory, skills, goal, style, tools, attachments.

## Files in chat

The paperclip in the composer attaches a file to your **next message** only. Attachments appear as cards above the input — they are not pasted into the text box, so nothing is sent twice by accident.

## Limits
| Limit | Value |
| --- | --- |
| Files per message | 8 |
| Per file | 256 KB |
| Per message, total | 1 MB |

The limits are enforced before the message is written: an oversized or binary file is rejected with one readable message and your composer stays intact.

## What can be attached
- Text-like files: `.md`, `.txt`, `.json`, `.csv`, source code, `.srt`.
- Story entries and chapters from the current project, attached as their own card.

Binary files (images, PDF, `.docx`) are not parsed; export the text first.

## How it reaches the model
Attached content is appended to the system prompt under *Attached files*, with name, kind and byte count. Long files are bounded and the prompt says when content was cut.

Files are stored with the message, so reopening a chat still shows the cards. Deleting the message or chat deletes its files.

## Models and prompt cache

## Capability chips
Every model row shows what it can do, from three sources:
1. **Known presets** — shipped facts for common models: context, output, reasoning, cache.
2. **Probe** — the *Verify* button asks the provider what it accepts.
3. **Observation** — usage numbers from real replies.

Chips are advisory. A model that claims no reasoning still works; the thinking control simply hides itself in `auto` mode.

## Per-model tuning
Settings → Models → *Edit* opens the model card: context window, output cap, temperature override, reasoning support, cache mode. Overrides are stored per `provider::model` pair.

## Prompt cache
Some providers reuse an unchanged prompt prefix and bill it cheaper. The chat footer shows cached tokens when the provider reports them:

- `cache 0%` — nothing reused.
- `cache 62%` — most of the prompt prefix came from cache.

Hits depend on a stable prefix. Editing older messages or changing the system prompt invalidates it — expected, not a bug.

## Thinking and reasoning

Models that support reasoning can spend tokens before answering. OpenPlot exposes that as **Thinking**.

## The control
The brain icon in the composer has three states: off, on, and *auto* (on for models that support it). With `thinkingUi = auto`, models that cannot reason do not see the control at all.

## Budget
The budget is the maximum reasoning tokens for this chat, clamped by the model's context window. A larger budget is not automatically better: it costs latency and money, and most tasks finish reasoning well before the cap.

## Where the output goes
Reasoning streams into a collapsible block above the reply. `thinkingDisplay` decides:
- **auto** — expands while streaming, collapses when the answer starts.
- **expanded** / **collapsed** — pinned.

Reasoning text is stored with the message and is never injected back into later prompts.

## Practical settings
| Task | Budget |
| --- | --- |
| Quick edits, chat | off |
| Planning, critique | 1–2k |
| Hard continuity or plot problems | 4k+ |

## Skills

A skill is a named block of instructions injected into the system prompt: continuity rules, a critique protocol, a genre guide. Skills are global; each chat can mute them.

## Builtins
Six ship with the app: continuity, prose, dialogue, pacing, beta reader and architect. They are marked **Builtin**:
- you can edit the text,
- **Reset** restores the shipped version,
- you cannot delete them.

## Adding a skill
Settings → Skills → **Add skill** opens the editor with name, description, content and a live preview of the injected block. **Save** creates it **disabled** — nothing reaches the model until you press **Enable**, so a half-written skill can never affect a reply.

Start from a template (Blank, Line editor, Beta reader, Worldbuilding) or import a `.md` file. Export produces a portable markdown file.

## Per-chat control
The composer shows a `Skills n` chip when skills are active. The popover lists every enabled skill with a switch; turning one off stores its id in the chat's opt-out list, so it stays off for that chat only.

## Prompt size
The skills block is capped at 12,000 characters. A skill that does not fit is replaced by `[skill truncated: …]` rather than cut mid-instruction.

## When skills hurt
Three overlapping skills often contradict each other. Keep two or three enabled per project and let agent.md carry the general rules.

## agent.md

agent.md is your permanent instruction file. It is injected into every chat under the label *Agent instructions (highest priority after the system prompt)*.

## What belongs there
- Voice and craft rules that apply to everything you write.
- Tool etiquette: read before write, ask before destructive edits.
- What the model must never do.

What does **not** belong there: story facts (story bible), reusable workflows (skills), one-off instructions (the message itself).

## Priority
1. System prompt and provider safety rules.
2. agent.md.
3. Project context.
4. Skills.
5. Reply style.
6. Memory.
7. Your message.

When two rules conflict the higher one wins; the model is told to say so in one line instead of silently picking.

## Editing
Settings → agent.md: edit, then **Preview prompt** to see the compiled result. **Restore default** loads the shipped text, templates give you a novelist, editor or minimal starting point, and the counter shows characters and approximate tokens.

Drafts survive switching sections; **Discard** throws them away.

## Upgrades
When a new version ships a better default, the app replaces agent.md **only if it still matches the old shipped text exactly**. If you changed a single character, nothing is touched — a one-time toast tells you the default moved on.

## Story bible

The story bible is per project: characters, locations, items, factions, lore, timeline and outline entries.

## Entries
Each entry has a **kind**, a **title**, **content** (markdown), **tags** and optional **links** to other entries. One fact per entry is what makes retrieval work — a single "everything about the war" entry is hard to search and hard to keep current.

## Tools the model uses
With tools enabled the model can `search_story`, `read_story_bible`, `create_story_entry` and `update_story_entry`. Writes come back as a summary of what changed and the view refreshes itself.

## Attach to a chat
A chat bound to a project receives the project description as context. Pull a specific entry into the composer instead of dumping the whole bible.

## Good canon hygiene
- One subject per entry, named the way you would search for it.
- Update entries when the story changes; stale canon is worse than none.
- Use links for relationships instead of repeating text.

## Chapters

Chapters hold the manuscript. Each chapter has a title, content, status (`draft`, `revising`, `done`), a position and a word count.

## Writing in the app
The editor saves when you press **Save** — nothing is written behind your back mid-sentence. Version history keeps a snapshot per save so you can compare or roll back.

## With the model
Ask for a scene and the model can `create_chapter`, `update_chapter`, `append_to_chapter` and `read_chapter`. Appending is safer than rewriting: it never touches what you already wrote.

Agents write to chapters, not to the chat, when the output is long-form. That keeps prose out of the transcript and out of the prompt history.

## Status and flow
Chapter status feeds Story Flow, which turns beats into chapters. Word counts feed Writing Stats.

---

## Story flow

Flow is the outline board: **acts → beats → chapters**.

## Beats
A beat is a title, a summary and a status (`planned`, `written`, `cut`). Move beats between acts, reorder them, and link one to a chapter when it becomes prose.

## Working with the model
The story agent can propose a beat sheet, expand one beat into a scene plan, or check that every act has a turn. Proposed plans live in `story_plans` until you accept them, so a bad suggestion never edits your outline.

## Practical loop
1. Beats for the current act only — future acts stay fuzzy.
2. Expand the next beat into a chapter when you sit down to write.
3. Mark the beat written once the chapter exists.

## Writing stats

Stats counts words you actually wrote, per day and per project. It is local and never uploaded.

## What counts
- Edits to chapter content, chat replies you keep, and story entries.
- Removed words count negatively, so copy-paste and deletion do not inflate the graph.
- Only deltas are recorded — rewriting the same sentence five times adds no words.

## Reading the graph
- **Today** resets at local midnight.
- **Streak** counts consecutive days with any positive delta.
- **Per project** shows where the writing went.

The numbers are approximate by design: this is a motivational graph, not an audit trail.

## Export

## Chat
- **Markdown** — the whole conversation with roles and timestamps.
- **JSON** — messages plus metadata, for processing elsewhere.
- Both are available from the palette (`Ctrl+K`) and the chat header.

## Chapters and projects
A project exports as one Markdown file or an EPUB, chapters in order, with the story bible appended as an appendix when you ask for it.

## Full backup
Settings → Data exports everything as JSON: chats, projects, story bible, chapters, prompts, styles, skills, settings. API keys are stripped.

Restoring is a merge, not a replace: rows with the same id are updated, new rows are added, nothing is deleted.

> Export before a version upgrade. It costs one click and it is the only backup the app does not make for you.

## Settings

Settings is grouped by what you are trying to do, not by data model:

- **AI** — providers, models, behaviour.
- **Chat** — styles, skills, agent.md.
- **Appearance** — theme, accent, font size.
- **Data** — memory, usage, backup and reset.
- **Extend** — plugins, automations, MCP *(advanced mode)*.
- **About** — version, data path, credential vault, guide.

## Search
The search box above the nav finds controls, not just sections: type `cache` to land on the cache rows of the models page. `↑`/`↓` move, `Enter` jumps and focuses the control, `Esc` clears.

## Simple vs advanced
Simple mode hides advanced model parameters and the Extend group. Nothing is removed — *Show advanced settings*, also in the palette, brings everything back, and the choice is remembered.

## Reset
Each section can reset its own defaults. *Reset all data* in Settings → Data deletes everything and cannot be undone; export first.

## Plugins

A plugin is a local JavaScript file with hooks. Plugins run in the main process with the same access as the app: install only code you wrote or read.

## Shape
```js
module.exports = {
  name: 'word-count-logger',
  hooks: {
    'message:new': (payload, api) => api.log('message ' + payload.role)
  }
}
```

## Hooks
Fired by the app today: `chat:new` (a chat row is created) and `message:new` (a message is saved).

`app:ready`, `chat:send`, `chapter:saved`, `project:created` and `skill:enabled` belong to the plugin API but are not wired yet — treat them as planned, and fire your own hook names if you need them now.

## Behaviour
- Disabled plugins are never loaded, not loaded and then blocked.
- Errors are caught per hook and written to the plugin's log; a broken plugin does not break chat.
- A plugin registers commands with `context.registerCommand`; the row list in Settings → Plugins shows its log.

See `docs/PLUGIN_API.md` in the repository for the full surface.

## MCP servers

MCP (Model Context Protocol) is how a model calls tools that live outside the app: a filesystem helper, a search index, a database.

## Status in this version

Settings → MCP stores server definitions locally — name, command, arguments, environment variables and an enable flag. **The bridge that starts those processes, lists their tools and exposes them to the model is not part of this version.** A stored definition never runs anything; enabling one is configuration for the release that ships the bridge.

The plan, and the protocol details, live in `docs/PLUGIN_API.md` and the release plan under `docs/superpowers/plans/`.

## What you can do today

- Keep the registry ready: add the servers you want, with the exact command and arguments, so enabling them later is one switch.
- Read the command before saving it. An MCP server runs as a local process with your permissions; treat a definition like a script you are about to run.

## What the bridge will do

- Spawn only enabled servers, after the window is ready, and kill them on quit.
- Speak newline-delimited JSON-RPC 2.0 over stdio: `initialize`, `tools/list`, `tools/call`.
- Advertise their tools as `mcp__{server}__{tool}` when tools are enabled, with a call timeout and a capped response size.
- Show a status dot per server (starting, connected, error), the tool count, the last error and a filtered log.

Until then, the app's own story tools are the ones the model can actually call — see the skills and story bible articles.

## Privacy and data

## Local by default
Everything is stored in a SQLite file in your user data folder, shown in Settings → Data: chats, messages, attachments, projects, story bible, chapters, prompts, skills, settings.

No analytics, no telemetry, no account.

## What leaves the machine
Only the request you send: the system prompt (which may include agent.md, project context, skills and attached files), the conversation history, and your message. It goes directly to the provider you configured — there is no proxy in between.

Images and files are sent as text. Binary files are rejected rather than uploaded.

## API keys
Keys are stored encrypted when the OS credential vault is available; otherwise the app says so in Settings → Data. They never appear in exports, logs or error messages.

## Deleting
*Reset all data* deletes every row and the file contents. Backups written during a schema migration (`.bak`) stay next to the database — remove them manually for a clean slate.

## Troubleshooting

## "No model selected"
The chat has no model and Auto could not resolve one. Pick a default in Settings → Models, or choose a model in the composer.

## 401 / 403 from a provider
The key is wrong, expired, or lacks access to that model. Re-paste it, then **Verify** the model.

## 404 or "model not found"
The model name does not exist for that provider, or the base URL is missing `/v1`. Use *Test & fetch* to see the real list.

## Empty replies with tools enabled
Some models emit a tool call and no text. The app retries once; if it persists, turn tools off for that chat or switch to a model with reliable tool use.

## Rate limits
Wait, or switch provider. The provider's error text is shown verbatim so you can see the reset time.

## The app feels slow
Long chats load the newest 80 messages first. If typing lags, close model popovers and check that the chat is not carrying dozens of attachments.

## Database problems
A failed migration leaves the file untouched and reports the error. Restore a `.bak` copy next to the database, or export from another machine.

Still stuck? The repository issue tracker is the fastest route: include the version from Settings → About and the exact error text.
