# OpenPlot AI v1.2.5 — Reliability Patch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a small, low-risk patch that makes upgrades safe (versioned migrations + backup), stops users from silently running an old build (update notice), and locks in the v1.2.0 performance work with a repeatable benchmark.

**Architecture:** Three independent additions, each behind its own module. `electron/db.ts` gains a numbered migration list driven by `PRAGMA user_version` with a pre-migration backup file. A new `electron/updates.ts` performs one HTTPS request to the GitHub releases API, caches the answer in the existing `settings` table, and exposes it over IPC; the renderer renders a dismissible notice. A standalone benchmark script measures the write path so regressions are visible before release.

**Tech Stack:** Electron 33 main process (Node built-ins only — no new runtime dependency), React renderer, sql.js SQLite, the existing `scripts/run-all-tests.mjs` headless harness.

**Spec:** This document. Source material: the v1.2.0 post-release review recorded in `CHANGELOG.md` §1.2.0 and the carry-over list at the end of this plan.

## Global Constraints

- **No new runtime dependencies.** Update checking and version comparison use `node:https` / `node:url` and a local `compareVersions`; do not add `semver` or `electron-updater`.
- **Local-first invariants hold.** No account, no telemetry, no network request that blocks startup. The only new outbound request is a single `GET https://api.github.com/.../releases/latest`, and its failure must be invisible.
- **Patch semantics.** No breaking change, no removal, no renamed IPC channel, no changed DB column type. Users on 1.2.0 must be able to open a 1.2.5 database and vice versa (1.2.5 only adds `user_version` bookkeeping).
- **All user-facing strings** are added to `src/i18n.ts` for **both** `en` and `id`.
- **Tests stay offline.** Headless suites may only talk to localhost mocks; the update-check test injects a fake request function, never the real API.
- **Version string appears in four places** and all must match: `package.json`, `package-lock.json` (root `version`), README download table, and the `VER` fallback in `docs/index.html` + `docs/id/index.html`.

## Review Focus

- **GitHub API rate limit / offline / DNS failure:** the app must start, look normal, and simply have no notice. No toast, no delay on first paint.
- **Pre-release and non-semver tags** (`v1.3.0-beta.1`, `latest`, `v2`): must not be offered as an upgrade.
- **Database newer than the app** (user downgrades, `user_version` > `SCHEMA_VERSION`): must refuse to migrate, keep the file untouched, and surface a readable error instead of corrupting or silently continuing.
- **Interrupted migration** (process killed mid-run, disk full during backup): the original file must still open, and the next launch must retry cleanly.
- **Clock skew / stale cache** (`update.check.checkedAt` in the future): still re-checks, never wedges the notice permanently on or off.

### Task 1: Versioned schema migrations with pre-migration backup

**Files:**
- Modify: `electron/db.ts` (the `initDb` migration block at lines ~160-195, plus new exports near the schema)
- Create: `scripts/db-migration-test.mjs`
- Modify: `scripts/run-all-tests.mjs` (headless group array)

**Interfaces:**
- Produces: `export const SCHEMA_VERSION: number` (starts at `3`, the implicit v1.2.0 state), `export function getSchemaVersion(): number`, `export function migrateDb(targetVersion?: number): { from: number; to: number; applied: number[] }`.
- Produces: migration table `const MIGRATIONS: { version: number; statement: string }[]` — version = the version the statement *produces*, appended in order, never reordered.
- Consumes: existing module-level `db`, `dbFile`, `persistNow()`.

- [ ] **Step 1: Write the failing test**

`scripts/db-migration-test.mjs` builds three fixtures with sql.js directly in a temp dir:
1. fresh directory → `initDb` → `getSchemaVersion() === SCHEMA_VERSION`, no `.bak` file created;
2. legacy fixture: schema at v2 with `story.links` missing, `PRAGMA user_version = 0` → after `initDb`, the column exists, `user_version === SCHEMA_VERSION`, and one `openplot.db.v0.bak` exists;
3. reopen the migrated file → no second `.bak` is written and `applied.length === 0`.
Plus one assertion for `user_version = SCHEMA_VERSION + 1` → `initDb` rejects with a message matching `/newer version/i` and leaves the file byte-identical.

- [ ] **Step 2: Run it and watch it fail**

Run: `node scripts/db-migration-test.mjs`
Expected: FAIL — `getSchemaVersion is not a function`.

- [ ] **Step 3: Implement the migration runner**

Add `SCHEMA_VERSION = 3`; move every existing `try { db.exec('ALTER TABLE …') } catch {}` line into ordered `MIGRATIONS` entries (v1 → v2 → v3 statements keep their current order; `CREATE TABLE IF NOT EXISTS` statements for `story_files` / `story_plans` / indexes belong to the v3 entry). In `initDb`, after the schema exec:

```
const from = readUserVersion();          // PRAGMA user_version, 0 when absent
if (from > SCHEMA_VERSION) throw new Error(`Database was created by a newer version (schema ${from} > ${SCHEMA_VERSION}). Update OpenPlot AI.`);
if (from > 0 && from < SCHEMA_VERSION) backupOnce(from);   // fs.copyFileSync(dbFile, `${dbFile}.v${from}.bak`) unless it already exists
db.exec('BEGIN'); try { apply steps; db.exec(`PRAGMA user_version = ${SCHEMA_VERSION}`); db.exec('COMMIT'); } catch (e) { db.exec('ROLLBACK'); throw e; }
```

A fresh database (`from === 0` **and** no file on disk) skips backup and only stamps `user_version`. Keep the pre-migration dump (`db.export()`) in memory before `BEGIN`, and restore from it on failure so the running instance keeps a usable database.

- [ ] **Step 4: Register the suite**

Append `'db-migration-test.mjs'` to `GROUPS.headless` in `scripts/run-all-tests.mjs`, right after `'db-test.mjs'`.

- [ ] **Step 5: Verify and commit**

Run: `npm run build:electron && node scripts/db-migration-test.mjs && npm test`
Expected: new suite prints `PASS`, existing suites unchanged.
Commit: `feat(db): versioned migrations with pre-migration backup`.

### Task 2: Update availability notice

**Files:**
- Create: `electron/updates.ts`
- Modify: `electron/main.ts` (IPC handler + 6-hour timer after `ready`), `electron/preload.ts` (`checkForUpdate`, `onUpdateNotice` not needed — renderer pulls on mount)

**Interfaces:**
- Produces (main): `export function compareVersions(a: string, b: string): -1 | 0 | 1`, `export function parseLatestRelease(json: unknown): { version: string; url: string } | null`, `export async function checkForUpdate(opts: { current: string; fetchJson?: () => Promise<unknown>; now?: () => number; cache?: { checkedAt?: number; latest?: string; url?: string }; force?: boolean }): Promise<{ version: string; url: string; isNewer: boolean } | null>`
- Produces (preload): `checkForUpdate(force?: boolean)` → the same object or `null`.
- Produces (settings rows): `update.check` = `{"checkedAt":number,"latest":string,"url":string}`; `update.dismissed` = `"1.2.5"`.

- [ ] **Step 1: Write the failing tests**

`scripts/update-check-test.mjs` covers: `compareVersions('1.2.5','1.2.10') === -1`; equal strings → `0`; `v`-prefix tolerated; `1.3.0-beta.1` and `latest` rejected by `parseLatestRelease`; `isNewer` false when equal; cache honored inside 24 h and bypassed with `force: true`; `checkedAt` in the future still triggers a re-check; a rejected `fetchJson` resolves to `null` instead of throwing.

- [ ] **Step 2: Run and watch it fail**

Run: `node scripts/update-check-test.mjs`
Expected: FAIL — module not found.

- [ ] **Step 3: Implement `electron/updates.ts`**

`node:https` GET with `User-Agent: OpenPlot-AI/${current}`, `Accept: application/vnd.github+json`, 6 s timeout, 128 KiB response cap, `res.resume()` on overflow. Parse `tag_name` + `html_url`; return `null` for anything that does not match `/^v?\d+\.\d+\.\d+$/`. Cache in the `settings` table through the existing get/set helpers; 24 h TTL.

- [ ] **Step 4: Wire IPC, preload and UI**

`ipcMain.handle('app:updateCheck', (_e, force?: boolean) => …)` returning `{ ok: true, data }` like the other handlers; schedule the first check 10 s after window creation (never before) and repeat every 6 h. `UpdateNotice` renders only when `isNewer` and `settings.update.dismissed !== latest`; it is one line tall, has a `×` that persists dismissal, and opens `html_url` through the existing `openExternal` (https-only guard already exists). About gains "Check now" calling `checkForUpdate(true)` with a toast for "up to date" / "new version found".

- [ ] **Step 5: Verify and commit**

Run: `npm run typecheck && npm run build && npm test`
Expected: all green; `update-check-test.mjs` PASS.
Commit: `feat(app): notify when a newer release exists`.

**Files:**
- Create: `scripts/bench-db.mjs`
- Modify: `package.json` (`"bench": "node scripts/bench-db.mjs"`)

**Interfaces:**
- Produces: a printed table and, with `--assert`, a non-zero exit when a threshold regresses.

- [ ] **Step 1: Implement the benchmark**

## Out of Scope

- **Code signing / notarization** — needs certificates and an Apple developer account; it is a distribution project, not a patch.
- **Auto-update installation** — macOS requires a signed build, so this only becomes possible after signing; the notice in Task 2 is the honest intermediate step.
- **Undo history for agent writes** — needs a new audit table plus inverse operations and a UI; scheduling it here would double the release.
- **Cloud sync, mobile, collaboration** — conflicts with the local-first invariant unless explicitly opt-in.

## Risks and Rollback

- Migration bug → the `.bak` file plus the in-memory restore path keep the original database openable; rollback is "ship 1.2.0 assets again", since 1.2.5 adds no columns.
- Update check misparses a tag → `parseLatestRelease` returns `null` and nothing renders; worst case is a missed notice, never a broken app.
- Benchmark thresholds too tight on slow CI → thresholds live in the script and are only enforced by the manual `npm run bench -- --assert`, not by `npm test`.

1 → 2 → 3 → 5, with 5.1 (docs) startable in parallel. Task 1 ≈ 0.5-1 day, Task 2 ≈ 1 day, Task 3 ≈ 0.5 day, Task 5 ≈ 0.5 day: **2.5-3 days**; Task 4 adds 1-1.5 days if included.
